# ADR-003. SQLite в демо, PostgreSQL + RLS как production-blueprint

- **Статус:** принято
- **Дата:** 2026-11-07
- **Контекст:** демо должно запускаться без внешней инфраструктуры, но архитектура
  не должна выглядеть как «игрушечная база».

## Контекст

Для демо нужны три кейса, пользователи, карточки и их подписи. Всё это должно
переживать перезапуск, но не требовать установленного сервера БД, пароля и сети
в зале. При этом жюри оценивает техническую реализацию, и ответ «у нас SQLite,
потому что проще» звучит слабо, если рядом нет плана production-хранилища.

## Решение

Два уровня, явно разделённые:

1. **Runtime демо — SQLite** (`backend/merilo.db`, путь переопределяется
   `MERILO_DB_PATH`). Схема и сидинг выполняются в `lifespan` при старте, повторный
   запуск идемпотентен. Соединение открывается на операцию, включены `WAL` и
   `busy_timeout=5000`.
2. **Production-blueprint — PostgreSQL** (`sql/supabase_schema.sql`): 5 таблиц,
   индексы, внешние ключи и RLS-политики Supabase.

Важная честность: **RLS в демо не активен.** SQLite не применяет политики
PostgreSQL, файл — декларация целевой архитектуры, а не работающая защита.
В README и `docs/DEPLOY.md` это написано прямым текстом.

## Альтернативы

| Вариант | Почему отклонён |
|:---|:---|
| PostgreSQL в демо | Требует сервера/контейнера и креденшелов; риск не запуститься в зале |
| Только SQLite, без blueprint | Не видно, как проект масштабируется и закрывается по доступам |
| ORM (SQLAlchemy) | Лишний слой для 5 таблиц; SQL виден и проверяем как есть |

## Последствия

**Плюсы**

- Демо: ноль внешних зависимостей, файл БД удаляется одной командой.
- Детерминизм: свежая база + один и тот же ввод → один и тот же `card_hash`
  (проверено на двух независимых томах: `8c101d0a2a98`).
- Миграция описана заранее, а не «потом придумаем».

**Минусы и как компенсировано**

- SQLite — один писатель, нет репликации и RLS → в README это в разделе ограничений.
- Два диалекта SQL → blueprint не исполняется в тестах; проверяется синтаксически
  и ревью, а не прогоном.

## Доказательства

- `backend/db.py:181` — `get_db_connection` (WAL, `busy_timeout`).
- `backend/main.py:136` — `lifespan`: `init_db` + идемпотентный сидинг.
- `sql/supabase_schema.sql` — таблицы, индексы, RLS-политики.
- `docs/DEPLOY.md` — диск, переменные, ограничения SQLite.
