# Архитектурные решения (ADR)

Записи о решениях, которые определяют форму проекта. Формат: контекст → решение →
альтернативы → последствия → доказательства. Цель — чтобы человек, открывший
репозиторий через месяц, понимал не только «что сделано», но и «почему так, а не иначе».

| # | Решение | Ключевой компромисс |
|:---|:---|:---|
| [ADR-001](ADR-001-single-port-monolith.md) | Один процесс FastAPI раздаёт API и статику | Нет сборки и CORS, но и нет code splitting |
| [ADR-002](ADR-002-three-gate-pipeline.md) | Три шлюза по возрастанию стоимости | Regex не понимает смысл атаки |
| [ADR-003](ADR-003-sqlite-demo-postgres-blueprint.md) | SQLite в демо, PostgreSQL + RLS как blueprint | RLS в демо не активен |
| [ADR-004](ADR-004-card-hash-and-hmac.md) | Детерминированный `card_hash` + HMAC-подпись | HMAC — доверие серверу, не публичная криптография |
| [ADR-005](ADR-005-deterministic-fallback.md) | AST-fallback вместо заготовленных оценок | Эвристика грубее модели, и это подписано |

## Как читать

- **Статус «принято»** — решение действует в текущем коде.
- В каждом ADR есть раздел «Доказательства» со ссылками на файлы и тесты: решение
  можно проверить, а не принимать на веру.
- Если решение перестанет быть верным, создаётся новый ADR со статусом
  «заменяет ADR-NNN», а старый помечается «устарело». История не переписывается.
